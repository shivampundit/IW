DBMS & SQL — 30 Golden Rules & Normalization Cheat Sheet

Normal form rules (1NF to BCNF), ACID recovery, 2PL locking protocols, B+ tree properties, and SQL execution order.

Normal Form: 2NF Rule

No Partial Dependencies. No non-prime attribute can depend on a proper subset of candidate key.

Normal Form: 3NF Rule

No Transitive Dependencies. For X -> A: Either X is Superkey OR A is Prime Attribute.

Normal Form: BCNF Rule

Strict 3NF. For every non-trivial X -> A: X MUST be a Superkey (no exceptions!).

SQL: TRUNCATE vs DELETE

DELETE: DML, row logged, WHERE allowed.
TRUNCATE: DDL, deallocates pages, no WHERE.

SQL: Execution Order

FROM -> WHERE -> GROUP BY -> HAVING -> SELECT -> ORDER BY.

SQL: Three-Valued Logic

col = NULL yields UNKNOWN.
Always use IS NULL or IS NOT NULL.

2PL: Conflict Serializable

Growing phase acquires locks; Shrinking phase releases locks. Precedence graph is Acyclic.

B+ Tree: Leaf Node Links

Data records strictly in leaves; all leaf nodes linked in doubly linked list for range queries.

Decomposition: Lossless

R1 ∩ R2 must be a candidate key in R1 or R2: (R1 ∩ R2 -> R1) OR (R1 ∩ R2 -> R2).

20 Golden Exam One-Liners (Quick Revision)

1. A Candidate Key is a minimal superkey (removing any attribute destroys uniqueness).
2. Entity integrity mandates that primary key attributes cannot contain NULL.
3. Referential integrity requires foreign keys to match an existing primary key or be NULL.
4. Cartesian product of relations with degrees d1, d2 and cardinalities c1, c2 has degree d1+d2 and cardinality c1*c2.
5. A table can have at most ONE clustered index because physical data can only be sorted in one order.
6. In ER diagrams, weak entities are shown as double rectangles with partial keys underlined by dashed lines.
7. A Many-to-Many (M:N) binary relationship requires 3 relational tables (including a junction table).
8. 1NF requires all attributes to be atomic scalar values (no repeating groups).
9. 2NF eliminates partial dependencies; 3NF eliminates transitive dependencies; 4NF eliminates multi-valued dependencies.
10. 3NF always guarantees both Lossless-Join and Dependency Preservation; BCNF cannot always preserve all dependencies.
11. Durability in ACID ensures committed transactions persist across power outages via Write-Ahead Logging (WAL).
12. A Dirty Read occurs when a transaction reads uncommitted data from another transaction that later aborts.
13. A schedule is conflict serializable iff its Precedence Graph is acyclic (contains no cycles).
14. Strict 2PL holds all Exclusive (X) locks until commit/abort to prevent cascading rollbacks.
15. In B+ trees, non-root internal nodes of order m must contain at least ⌈m/2⌉ child pointers.
16. Standard aggregate functions (`SUM`, `AVG`, `MIN`, `MAX`) ignore NULL; `COUNT(*)` counts all rows.
17. `WHERE` filters rows before grouping; `HAVING` filters aggregate groups after `GROUP BY`.
18. Checkpoints flush dirty buffer pool pages to disk, bounding the log scan distance during crash recovery.
19. In relational algebra, Selection (σ) filters rows; Projection (π) selects columns and eliminates duplicates.
20. In Thomas' Write Rule, obsolete write operations with `TS(T) < W-timestamp(X)` are ignored rather than aborted.

(4) Durability: Committed updates persist permanently on non-volatile storage (Redo log/WAL).) — [Hinglish Tip / Memory Hook: Durability guarantees committed transactions survive system crashes. | Common Distractor Traps to Avoid: Atomicity; Consistency.]
  • Golden One-Liner #3: Exam Application (DSSSB PGT 2021): What concurrency anomaly occurs when Transaction T1 updates a data item and uncommitted T1 aborts, but Transaction T2 has already read that uncommitted value? => Correct Solution: Dirty Read (Write-Read Conflict). (Dirty Read (Uncommitted Dependency): Occurs when T2 reads data written by T1 before T1 commits. If T1 subsequently rolls back/aborts, the data read by T2 never physically existed, leading to data corruption.) — [Hinglish Tip / Memory Hook: Reading data written by an uncommitted transaction is a Dirty Read. | Common Distractor Traps to Avoid: Lost Update Problem; Non-Repeatable Read (Read-Write Conflict).]
  • Golden One-Liner #4: Exam Application (DSSSB TGT CS 2021): What graph algorithm is used to test whether a concurrent transaction execution schedule is 'Conflict Serializable'? => Correct Solution: Constructing a Precedence Graph (Serialization Graph); the schedule is conflict serializable if and only if the graph contains NO CYCLES (Acyclic). (Conflict Serializability Test: Construct a directed Precedence Graph where nodes represent transactions and a directed edge T_i -> T_j exists if T_i performs a conflicting operation on data item X before T_j. The schedule is conflict serializable iff the precedence graph is an acyclic graph (no cycles).) — [Hinglish Tip / Memory Hook: Precedence Graph must be acyclic (no cycles) for conflict serializability. | Common Distractor Traps to Avoid: Dijkstra's shortest path algorithm; Floyd-Warshall algorithm.]
  • Golden One-Liner #5: Exam Application (DSSSB PGT 2021): What are the rules governing the Two-Phase Locking (2PL) protocol? => Correct Solution: Growing Phase: A transaction may obtain locks but may not release any lock; Shrinking Phase: A transaction may release locks but may not obtain any new lock. (Two-Phase Locking (2PL): Guarantees Conflict Serializability. Phase 1 (Growing Phase): Transaction acquires all required locks (Shared/Exclusive) and releases none. Lock point is reached. Phase 2 (Shrinking Phase): Transaction releases locks and can acquire no new locks. Note: Basic 2PL is subject to deadlocks.) — [Hinglish Tip / Memory Hook: Growing phase acquires locks; Shrinking phase releases locks. | Common Distractor Traps to Avoid: Locks must be held for exactly 2 seconds; Every transaction must lock all tables at startup.]
  • Golden One-Liner #6: Exam Application (DSSSB TGT CS 2021): How does 'Strict 2PL' prevent cascading rollbacks in database systems? => Correct Solution: It requires that all Exclusive (X) locks held by a transaction be retained until the transaction COMMITS or ABORTS. (Strict 2PL: Standard 2PL allows releasing exclusive locks during the shrinking phase before commit, which can cause Cascading Aborts (other transactions read dirty data). Strict 2PL mandates holding all Exclusive (X) locks until the transaction is committed or aborted, guaranteeing strict, recoverable schedules.) — [Hinglish Tip / Memory Hook: Strict 2PL holds exclusive locks until transaction commits or aborts. | Common Distractor Traps to Avoid: It requires all shared locks to be held forever; It executes transactions one at a time.]
  • Golden One-Liner #7: Exam Application (DSSSB TGT 2021): What is the 'Write-Ahead Logging' (WAL) protocol used by database recovery managers? => Correct Solution: Log records describing changes MUST be written to non-volatile disk before the corresponding dirty data page is written to database disk storage. (Write-Ahead Logging (WAL): Fundamental database recovery axiom. Before any modified database block is flushed from RAM buffer pool to disk (Steal policy), the corresponding log record must be forced to disk. This ensures that the system can always UNDO uncommitted transactions after a crash.) — [Hinglish Tip / Memory Hook: Log records must be flushed to disk before data pages are flushed. | Common Distractor Traps to Avoid: Writes must be performed before reading; Logs are written once per day.]
  • Golden One-Liner #8: Exam Application (DSSSB PGT 2021): In Timestamp-Based Concurrency Control (Thomas' Write Rule), what happens if a transaction T with timestamp TS(T) attempts to WRITE to data item X, and TS(T) < R-timestamp(X)? => Correct Solution: Transaction T is rejected/aborted and rolled back with a new timestamp. (Basic Timestamp Ordering: If TS(T) < R-timestamp(X), it means a younger transaction has already read the value of X, assuming T's write had already occurred. Allowing T to write now would invalidate that read. Therefore, T's write request is rejected and T is rolled back.) — [Hinglish Tip / Memory Hook: If TS(T) < R-timestamp(X), T is too old and is aborted. | Common Distractor Traps to Avoid: The write operation is permitted; Transaction T ignores the read timestamp.]
  • Golden One-Liner #9: Exam Application (DSSSB TGT CS 2021): What is a 'Checkpoint' in database transaction log management? => Correct Solution: A periodic synchronization point where all dirty buffer pages and log records are flushed to disk, allowing the recovery manager to truncate older log records prior to the checkpoint. (Checkpoints: Without checkpoints, crash recovery would require scanning and processing the entire transaction log since database inception. During a checkpoint, the engine flushes all modified pages to disk and records active transaction IDs. Upon reboot, recovery only needs to scan back to the checkpoint.) — [Hinglish Tip / Memory Hook: Checkpoint flushes dirty pages, limiting log scan during crash recovery. | Common Distractor Traps to Avoid: A software breakpoint in SQL queries; A table constraint checking positive integers.]

  • Golden One-Liner #2: Exam Application (DSSSB TGT CS 2021): What is the primary difference between a B-Tree and a B+ Tree index? => Correct Solution: In a B-Tree, search keys and data records/pointers are stored in both internal nodes and leaf nodes; In a B+ Tree, data records/pointers are stored ONLY in leaf nodes, while internal nodes store only routing keys, and all leaf nodes are linked sequentially. (B-Tree vs B+ Tree: In B+ Trees, internal nodes store only routing search keys and child pointers, resulting in much higher branching factor (fan-out) and shorter tree depth.   • Golden One-Liner #3: Exam Application (DSSSB PGT 2021): What is the difference between a Primary Index and a Secondary Index? => Correct Solution: A Primary Index is built on an ordered data file sorted by primary key (sparse index); a Secondary Index is built on an unordered field or non-primary key and is typically dense. (Primary vs Secondary Index: A Primary Index is defined on an ordered data file where records are physically sorted on the indexing key (clustering property); it can be a sparse index (one entry per disk block).   • Golden One-Liner #4: Exam Application (DSSSB TGT CS 2021): What is a 'Clustered Index' in relational database storage engines (e.g., MySQL InnoDB)? => Correct Solution: An index where the physical order of table rows on disk matches the logical order of the index key (a table can have at most ONE clustered index). (Clustered Index: The table data rows themselves are physically stored in the leaf nodes of the index tree sorted by the clustered key (in InnoDB, the primary key). Because physical data can only be sorted in one order on disk, a table can have at most ONE clustered index.) — [Hinglish Tip / Memory Hook: A table can have at most ONE clustered index (physical sort order). | Common Distractor Traps to Avoid: An index that connects multiple computers in a cluster; An index with no duplicate keys.]

(B+ Tree Node Capacities: An internal node of order m can have at most m child pointers and m - 1 keys.   • Golden One-Liner #6: Exam Application (DSSSB PGT 2021): What is a 'Sparse Index' versus a 'Dense Index'? => Correct Solution: A Dense Index has an index record for EVERY search key in the data file; a Sparse Index has index records for only SOME of the search keys (typically one per disk block).
